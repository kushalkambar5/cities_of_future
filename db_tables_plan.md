9. Dynamic Vehicle Observation Matching
This replaces the old:
camera_segments

There is no camera_segments table.

Instead, we dynamically determine whether a vehicle has travelled too fast between CCTV cameras.
Logic
When a meaningful vehicle observation is obtained:
New vehicle observation
        ↓
Same plate?
        ↓
Search previous 10 minutes
        ↓
Previous CCTV within 5 km?
        ↓
Get route distance
        ↓
Calculate average speed
        ↓
Compare with speed limit
        ↓
Create violation if exceeded

Example
10:00
CCTV-01 detects KA01AB1234

        ↓ 4 minutes

10:04
CCTV-07 detects KA01AB1234

If:
CCTV distance = 3.8 km
Route distance = 4.6 km
Time difference = 4 minutes

Then:
Average speed
= 4.6 / (4/60)
= 69 km/h

If speed limit is:
60 km/h

then:
69 > 60
     ↓
OVERSPEED violation

11. route_distance_cache
This stores route distances between CCTV locations after obtaining them from the routing service.
route_distance_cache
─────────────────────
id
camera_a_id
camera_b_id
distance_meters
provider
created_at
updated_at

Why?
We don't want to request route distance every time.

Instead:
CCTV A → CCTV B
       ↓
Check cache
       ↓
Found?
 ├── YES → use cached distance
 └── NO  → routing service
              ↓
         save in cache

Important distinction
This is not a replacement for manually configured camera_segments.

camera_segments would define a permanent logical relationship.

route_distance_cache only caches a calculated route distance.

The relationship between cameras remains dynamic.

19. Why Notifications Are Separate
Don't put:
whatsapp_sent

inside fines.

Instead:
Violation
    ↓
Fine
    ↓
Notification
    ↓
WhatsApp

This allows:
WhatsApp send
      ↓
   FAILED
      ↓
    RETRY
      ↓
    SUCCESS

and keeps notification logic independent from the fine itself.
